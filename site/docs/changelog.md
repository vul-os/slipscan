## [Unreleased]

### Fixed
- **A JSON `null` could not clear a nullable field on any HTTP endpoint, silently.** `Option<T>`'s `Deserialize` maps `null` to `None` without descending, so on an `Option<Option<T>>` patch field `{"note": null}` and `{}` arrived identical: an absent key and an explicit null were indistinguishable, and every clear was read as "leave unchanged". Every patch type the HTTP API accepts was affected — ten of them — and the failure was quiet in the worst way: the request succeeded, returned 200, and left the field exactly as it was. Fixed with a `double_option` deserializer, now carried by 23 annotated fields, plus a source-level coverage test so a new nullable field cannot be added without one. The desktop escaped this only because `dto.rs` hand-rolled `clear_*` booleans to work around it; those are deleted, and one convention now covers every surface.
- **Contacts, the catalogue and the stock ledger were complete and reachable from almost nothing.** All three were finished at every layer — schema, repo, service, tests — and wired to no meaningful surface: contacts on 1 of 7 operations, the catalogue 1 of 16, and **the stock ledger 0 of 9**. Meanwhile purchasing and sales wired all of their own operations onto foundations a user could not put a row into, because an order needs a `contact_id` and a stock line needs a `variant_id`. Every layer individually complete, every test green, and nothing detected it. All three are now on the CLI, the HTTP API, desktop IPC and the TypeScript client; `npm run reachable:check` is the ratchet that keeps them there, comparing every public `CoreService` method against the surface sources with test modules stripped, because a method called only from `#[cfg(test)]` looks wired and is not.
- **Pack rules are applied on every surface, not just where a pack was installed.** `slipscan_packs::register_classifier()` documents itself as "call it once at startup, in every binary that imports transactions", and no binary did — registration only happened inside `pack_install`. A process that had not installed a pack *that run* therefore skipped every `contains`, `regex` and `keyword` rule already in the database; only `merchant_exact` rules kept working, because installs seed those into core's own `merchant_mappings`. The CLI's `main()` and the desktop's `run()` now register at startup, covered by a before/after test on each surface.

### Added
- **Trade reaches the ledger — stock movements now post double-entry journals** (migration `0016_ledger_trade`). Until now Phase 6 was an inventory app sharing a binary with an accounting app: a confirmed sale moved stock and recognised nothing. A goods receipt posts DR Inventory / CR Accounts Payable; confirming a sale posts DR COGS / CR Inventory alongside DR Accounts Receivable / CR Revenue and VAT Output; recording a payment posts DR Bank / CR Accounts Receivable. Cancelling a confirmed order **reverses rather than deletes**, because SQLite itself refuses to amend a posted journal — the `journals_no_update` / `journals_no_delete` triggers have stood since `0001_init`, and widening the `source_type` check in `0016` required rebuilding the table and restoring every one of them rather than dropping the guarantee for a migration. Posting is idempotent, refuses to write into a locked period, and when a book has no chart of accounts it posts nothing and says so rather than failing the trade. Revenue is recognised **exactly once per sale, on the path matching how the sale happened** — at confirm for an order-backed sale, at issue for a standalone invoice; getting that wrong leaves Accounts Receivable negative by exactly what was collected while every journal still balances, which no trial balance can show you.
- **Every financial report takes a date range, so a filing period is expressible at last.** `journals.posted_date` existed and not one routed report used it, which meant a VAT201 for a filing period — the single most ordinary thing a South African book needs — could not be produced at all. Core's date-aware implementations are now routed on every surface. This also settled the standing question of two report implementations rather than deferring it: core's are a strict superset of the all-time duplicates in `slipscan-server::ops`, so those were deleted instead of reconciled, and there is one accounting engine again.
- **Period close — `close check`, `close run`, `close reopen`.** `close check` is a dry run reporting exactly what `close run` would do; `close run` locks the period; `close reopen` is deliberate and audited and refuses without a reason. What blocks a close is deliberately narrow: **only a broken trial balance or a close dated before an existing one.** Uncategorised transactions, unreconciled lines, draft orders and unpaid invoices are all reported as advisories and none of them block, because a period end is a date, not a state of tidiness, and a close that waits for perfection is a close nobody performs.
- **Purchasing, sales and invoicing, and net worth over time.** Purchase orders with goods receipts against them. Sales orders moving draft → confirmed → paid, with an immutable invoice entity, gapless per-book numbering, recorded payments, derived paid/unpaid status and an aged receivables view. Invoice numbers are allocated by a single atomic `INSERT … ON CONFLICT DO UPDATE … RETURNING`, so the number and its reservation cannot come apart under concurrency — a two-statement allocate-then-read is a gap waiting for a second writer, and gapless numbering is a statutory requirement, not a preference. `networth_snapshots` captures a balance series and backfills one from existing history. **Multi-device invoice numbering remains unsolved**, and since nothing syncs, nothing yet forces the question.
- **Desktop screens for Phase 6 — Contacts, Catalogue, Stock, Purchasing, and Sales** (orders, invoices, aged receivables), each gated on the book profile so a household book is not shown a purchase order. These are the screens the roadmap listed as 6.9 and previously did not exist; the operations behind them had been reachable only from the CLI and the API.
- **`brand/` is the one source for brand assets, enforced by `brand:check`.** The mark and wordmarks were duplicated across five tracked locations with no sync step and nothing keeping them byte-identical past the first commit. `scripts/sync-brand.ts` mirrors the masters outward and fails CI when a destination drifts. The eight rendered PNGs are handled one step short: they are mirrored between their two locations but **never regenerated**, because nothing in the repo records the size, padding or export tool behind them and claiming otherwise would invent a provenance they do not have.
- **Four more CI gates, and none of them are taken on trust.** `parity:check` (the API surfaces match what the docs claim), `reachable:check` (no finished core capability is left unreachable), `mock-guards:check` (the desktop mock's guards still agree with core's), `tests:check` (every test asserts something, nothing is skipped, no `todo!()` ships) and `source:check` (no source file is accidentally binary — a single NUL byte makes `grep` skip a file *silently*, which had already produced one false-negative audit here). Each was mutation-tested rather than assumed: broken deliberately, confirmed red, reverted.
- **Bank-alert emails become transactions, with no bank's format in the product.** `slipscan mail-sync --alerts --account <acct>` parses a matched alert into a `StatementLine` and imports it through `import_statement_lines` — the same function CSV and scraper imports call — so dedupe, the categorisation cascade and the Payments detection hook all apply without a second implementation of any of them. Formats arrive as a third pack kind, `mailrules` (`crates/slipscan-packs/src/mailrules.rs`), inheriting ed25519 signing, TOFU signer pinning and per-book install; **SlipScan ships no bank patterns at all**, so `--alerts` has nothing to match until you install a pack and says exactly that. The engine (`crates/slipscan-ingest/src/email/alerts.rs`) contains no bank, country, currency or date-order literal, and declines with a reason rather than guessing — a letter inside a captured amount, a decimal separator disagreeing with the rule's declared style, a date outside the message's own drift window, or an account hint contradicting the target all refuse. CLI-only, one target account per run, no desktop screen: [docs/EMAIL.md](docs/EMAIL.md#bank-alert-emails--transactions).
- **Pack distribution with no registry: `file:`, `folder:`, `git:` and `https://`.** The same signed bytes over any transport, because the signature is what is trusted and not the channel — every transport ends at one `verify_detached`, and an `index.json` is a hint that gets cross-checked against the verified payload rather than an authority. Publishers own a directory named for their key fingerprint, so two people sharing one folder, Syncthing share or USB stick never write the same path. `pack source add|remove|list`, `pack fetch`, `pack pull` and `pack publish` on the CLI; `pack_source_*` over HTTP and desktop IPC, with the Packs screen showing a publisher's fingerprint before you accept it. **No built-in source and no default URL exists anywhere in the tree**: the source list starts empty, so a fresh install makes zero pack network calls, `http://` and password-bearing URLs are refused, and a pack id whose signer key changed is refused outright. Format and distribution: [docs/PACKS.md](docs/PACKS.md).
- **A signed operation log — phase 2 of the node model, and still nothing syncs.** Every change to a replicated table is recorded as one DMTAP Sync operation (`substrate/SYNC.md` §4), individually signed with the device key phase 1 minted (RFC 9052 `COSE_Sign1`, EdDSA, the substrate's DS-tag), ordered by a persisted HLC, and stored in the same SQLite file as the books. Capture is a **SQLite trigger per replicated table** (migration `0700_oplog`), not a call from the repo layer: a trigger catches a cascading delete, a migration and an importer nobody has written yet, whereas a call site catches only what somebody remembered to instrument — and the trigger set is asserted equal to `slipscan-sync`'s mapping registry in **both** directions, so a table added without a sync decision fails the suite instead of replicating by accident or silently not replicating. An operation has **exactly one identity**, the §4.1 content address, which is the primary key — never a content address beside a row id, because that is two identities that disagree. Money stays `i64` minor units end to end. The log is append-only and SQLite refuses to update it; the posted ledger stays immutable through all of it, because migration `0101` already blocks `UPDATE`/`DELETE` on `journals` and `journal_lines`, so those tables carry an insert capture trigger and no others and a correction remains a reversal. The clock carries a **drift bound above the engine**, deliberately looser than the engine's ingest bound because the two answer different questions: sealing refuses only when this machine's clock is more than a day out, which is drift that will never resolve itself and would be unfixable once signed. `slipscan sync status|seal|log|verify`. **There is still no transport and no apply path** — nothing carries an operation to another machine and nothing applies one that arrived, so **pairing two devices still changes nothing about your data**. There is no desktop surface either; what one would need is written down rather than half built: [docs/NODES.md](docs/NODES.md#what-is-still-missing).
- **Per-device identity and pairing — phase 1 of the node model, and nothing syncs.** An ed25519 keypair per device whose public half *is* the device id, private half in the existing write-only vault; migration `0600_devices`; peers pinned trust-on-first-use where a key change is a refusal rather than a silent re-pin and a revoked peer becomes a tombstone that cannot re-pair itself; identity rotation must be signed by the key it replaces; 9-word key-names so two people can compare a fingerprint out loud. **No accounts anywhere in it** — no email, password, username, login, or server that decides who you are. `slipscan device` runs the whole ceremony; over HTTP only the public half is served — identity, peers, invite *metadata* and revocation — while anything creating key material or carrying a claim token is local-only and answers 403 with the command to run, because an absent route reads like an oversight and a refusal reads like a decision. There is no Devices screen in the desktop app. There is still no transport, so **pairing two devices changes nothing about your data**: [docs/NODES.md](docs/NODES.md).
- **[PARITY.md](PARITY.md) — the parity matrices [ROADMAP.md](ROADMAP.md) promised twice and never carried.** 24 capabilities across the Xero and Vault22 / 22seven axes, each scored Built / Partial / Not built with a link to the file that justifies the score, plus a ranked gap list. It does not round up: 2 built, 10 partial, 12 not built, and **zero of Xero's fourteen core capabilities**, invoicing included. `npm run docs:check` fails if any citation stops resolving.
- **`slipscan watch <dir>`** — scan a drop folder, import everything ingestable in it, then keep importing as files land; `--once` for cron/launchd. Content-hash dedup means a rescan never double-imports. The desktop app still has no watch-folder setting, and drag-and-drop is not built anywhere.
- **Seed packs are reachable.** `builtin::install_seed_packs` had no caller on any surface. It is now an explicit user action — `slipscan pack seed`, `POST /api/v1/pack_install_seeds`, and the desktop `pack_install_seeds` IPC command, surfaced on the Packs screen. Still opt-in and never automatic: which taxonomy a book starts from is the user's decision. Idempotent and non-clobbering.
- **`pack_uninstall` and `pack_benchmark` over HTTP; `pack uninstall` and `pack benchmark` on the CLI.** Uninstall existed only as a Tauri command; the comparison math in `slipscan-packs::benchmark` had no production caller at all. `ops::pack_benchmark` now feeds it a book's own spend for a month — core's spending report resolved onto pack taxonomy keys through the map installs already write, rolling child categories into their parent's key, never converting currencies and reporting a currency mismatch instead of a fabricated zero. Reading is entirely local and transmits nothing; benchmark **contribution**, and the differential privacy it needs, remain unimplemented ([docs/BENCHMARKS.md](docs/BENCHMARKS.md)).

### Changed
- **The repo's own JavaScript is now TypeScript — all seventeen files.** The eight root gate scripts in `scripts/`, the desktop app's build and screenshot scripts, and the app's API client. The gate scripts stay dependency-free and run under Node's native type stripping, so there is still no bundler and no build step for them; CI moved to Node 24 for it. The measurable win was not the annotations but the coverage: `svelte-check` went from 238 to **364 files**, because the converted files had been outside `tsconfig.json` and were type-checked by *nothing at all*. The only JavaScript left in the tree is vendored third-party code (`mermaid`, `marked`) which is not ours to convert. **The Rust crates are untouched** — SlipScan's core, CLI, server, extraction, ingestion, packs and sync are Rust and stay Rust. The compiler moved 5.9 → **6.0.3** with the whole suite clean on the first run: `svelte-check` 364 files and 0 errors, 308 unit tests, 43 e2e, and a production build. **TypeScript 7 is deliberately not taken.** 7 is the compiler rewritten in Go, and it does not expose the JavaScript compiler API that `svelte-check`, `svelte2tsx` and `typescript-eslint` all call into — all three cap at 6. Taking 7 would trade away the only type gate covering those 364 files for compile speed on a tree far too small to need it, so 6 is the end of the line here until the Svelte toolchain follows.
- **The desktop app's `lib/` is grouped by what each module is.** It had grown to seventeen loose files at one level beside `api/` and `components/`, mixing Svelte 5 rune stores, dependency-free helpers, platform glue and domain logic with nothing in the listing to tell them apart. `state/` now holds the seven rune stores and `util/` the four helpers that import nothing from the app. The six app-level modules stayed put rather than being forced into an invented category, and `api/status.svelte.ts` stayed with the API client it belongs to despite being a rune store — where a module lives should say more about it than its shape does.
- **Documentation honesty sweep — caveats that had stopped being true.** Every claim below was wrong in the *too-pessimistic* direction, which this repo treats as no better than overstating: a reader who believes a retired caveat makes decisions from it. Corrected against the code, with the surface gap named in each case rather than glossed: ROADMAP Phase 3 and 4.8 said bank-alert parsing was "not implemented" / "not wired yet"; Phase 4.95's alert-parser item was unticked; Phase 4's "Distribution with no central registry" was unticked; the device-sync block carried "per-device identity … and a transport" as one open item, now split so identity is ticked and the transport is not; Phases 1–3 said statement CSV parsing "is not wired to a surface" when `slipscan import --preset` has driven it since before 0.2.0, and Phase 2 said file watch was unwired when `slipscan watch` ships. Same class of staleness in `docs/BANK-ADAPTERS.md` (alert parsing "planned but not implemented"; statement wiring "in progress"), `docs/PAYMENTS.md` and `docs/SCREENSHOTS.md` (alert-driven detection "not implemented"), and `docs/ARCHITECTURE.md` + `docs/FAQ.md` (parity matrices "not yet written"). The README's device-sync bullet no longer claims device identity does not exist, and its network diagram no longer implies DP contribution is live.
- **Caveats that are still true were left standing, and some were sharpened.** Differential-privacy benchmark contribution is not built; nothing syncs between devices; drag-and-drop capture is not built; converted multi-currency report views are not built (the README now says outright that no report converts anything, instead of "still landing"); no push loop runs on any surface, so IMAP IDLE and Gmail Pub/Sub pull stay library-only — stated directly under the `docs/EMAIL.md` connectivity matrix, whose Push column was the easiest thing in the docs to misread; Microsoft Graph push remains Unsupported by design outside self-host mode; no adapter talks to a bank.
- **Payments dropped its separate product name.** What 0.2.0 shipped as "ShapePay" is documented as what it is — **Payments: reference watches and signed webhooks** — across the README, roadmap, `docs/PAYMENTS.md`, `docs/API.md`, CLI help, and the desktop panel. Wording only: no table, column, settings key, operation, CLI subcommand, Tauri command, or type changed, and migration `0400_shapepay` keeps its id (applied migration ids are history).

## [0.2.0] — 2026-07-19

- **ShapePay — email-driven payment webhooks (Phase 4.8).** Watch reference codes on inbound transactions (a flat list — whole-token matching, optional exact amount + currency) and fire HMAC-SHA256-signed webhooks (timestamp + nonce headers, receiver-verifiable, replay-safe) to endpoints you register. Signing secrets are generated locally, held write-only in the credential vault, and shown exactly once; deliveries queue in SQLite with exponential backoff (1m → daily, 20-attempt cap) and carry metadata only — never account numbers or raw bank descriptions. Surfaced as `slipscan pay` on the CLI, `pay_*` server routes (secret-bearing operations refused over HTTP), a serve-mode delivery loop, a `mail-sync` flush, and the desktop Payments panel. Guide with a receiver verification example: [docs/PAYMENTS.md](docs/PAYMENTS.md).
- **Movable data folder + bring-your-own-backup (Phase 4.75).** One data folder (SQLite + documents) relocatable from desktop Settings and `slipscan data move` via a verified copy (exclusive-lock WAL quiesce, per-file SHA-256, open/migrate + integrity check, fsync-durable atomic pointer swap, old copy removed only after the verified swap), resolved identically by CLI/server/desktop; backup is the user's own cloud sync on that folder (no SlipScan backup service; the keychain KEK never travels with it).
- **UI/UX pass.** Deep design-system layer (oklch elevation hairlines, grain overlay, motion tokens with a staggered route-enter reveal, branded focus-visible rings, display numeric scale, unified chips), per-screen polish across all routes with token-palette charts and semantic budget bars, responsive down to ~740px with a collapsing sidebar rail, and refreshed real-app screenshots.

## [0.1.0] — 2026-07-19

The rewrite: SlipScan rebuilt from the ground up as a fully local, self-hosted product — Rust core, Tauri 2 desktop app, embedded SQLite, zero default network calls. Architecture contract in [docs/ARCHITECTURE.md](docs/ARCHITECTURE.md). First packaged release: installers for macOS (.dmg), Windows (.msi / setup.exe), Linux (.AppImage / .deb) plus standalone CLI binaries on the [releases page](https://github.com/vul-os/slipscan/releases).

### Added
- **Global by default — region profiles.** Nothing country-specific is code: chart-of-accounts seeds, tax rate tables, and tax-report labels ship as selectable region profiles (`za` for South Africa — where the tax summary is labeled "VAT201" — and a `generic` profile with a configurable standard rate that works in any country). Bank statement presets are region-namespaced (five SA banks + eight generic international CSV conventions + a custom column mapper), and builtin packs include a global `intl-starter` merchant taxonomy alongside the SA packs.
- **Multi-currency FX via [OpenRate](https://github.com/vul-os/openrate)** — strictly opt-in (no endpoint configured means zero FX network calls): decimal-only rate parsing (floats never touch money), exact 256-bit integer conversion with banker's rounding, a local rate cache with `as_of`/quality-grade/staleness provenance, every conversion recording the exact rate it used; surfaced on CLI (`slipscan fx`), server routes, and desktop Settings.
- **Release packaging** — Tauri bundles for all three platforms and a tag-triggered CI release workflow (version-match guard, draft releases, commented signing hooks); Playwright screenshotter (`npm run screenshot`) keeps README/site/docs screenshots real.
- **Rust workspace foundation** — `slipscan-core` (domain model, SQLite storage with embedded migrations, service layer: books, accounts, transactions, categories, budgets, documents, double-entry ledger, VAT, reconciliation, reports, append-only audit log), `slipscan-cli` (`init`, `import`, `extract`, `mail-sync`, `recon`, `report`, `pack`, `vault`, `serve`, `list` — CSV export lives on `report … --csv`, there is no separate `export` subcommand).
- **Tauri 2 desktop app** scaffold (`apps/desktop`) — Svelte 5 + TypeScript + Vite + Tailwind v4; IPC commands as thin adapters over core services, with hand-maintained TypeScript payload mirrors.
- **Credential vault** — OS-keychain-rooted secret storage (`keyring`-backed `SecretStore`), envelope-encryption design with write-only semantics: secrets can be set, replaced, revoked, and used — never viewed. Design: [docs/THREAT-MODEL.md](docs/THREAT-MODEL.md).
- **Ingestion framework** (`slipscan-ingest`) — `MailboxConnector` trait for user-owned mailboxes (IMAP + IDLE; Gmail history deltas with Pub/Sub pull push; Microsoft Graph delta with device-code flow; Proton via local Bridge), `BankAdapter` trait for local, auditable per-bank adapters, and file import/watch. Guides: [docs/EMAIL.md](docs/EMAIL.md), [docs/BANK-ADAPTERS.md](docs/BANK-ADAPTERS.md).
- **Extraction pipeline** (`slipscan-extract`) — slip-v2 schema (line items, categories, discounts, VAT) with pluggable BYO-key or local LLM/OCR providers; document status machine `pending → extracted → reviewed`.
- **Signed classification packs** (`slipscan-packs`) — category taxonomies + merchant rules as ed25519-signed manifests, verified on install; corrections stay local. Guide: [docs/PACKS.md](docs/PACKS.md).
- **Headless self-host server** (`slipscan-server`) — axum wrapper over the same core services, `/api/v1` operation-per-route, binds `127.0.0.1:7151` by default with LAN bind as explicit opt-in. Guides: [docs/SELFHOST.md](docs/SELFHOST.md), [docs/API.md](docs/API.md).
- **Documentation set** — getting started, configuration, email, bank adapters, packs, benchmarks, self-host, API, threat model, screenshots, FAQ under `docs/`; root `SECURITY.md` reporting policy.

### Changed
- **README** rewritten for the standalone product: centered wordmark, plain-text badges (no external image fetches), hero screenshot, screenshot gallery, quick start, architecture + decentralized-network diagrams, and a full documentation table.

### Fixed
- **Reversal-aware correction path** (migration 0201): a generated journal that has been reversed no longer blocks regenerating a corrected journal for the same transaction/document, and reconciliation now treats a journal reinstated by reversing its reversal as matchable again. Uniqueness is enforced as "one *net-live* generated journal per source" in the service layer.
- **VAT classification**: the counter-account fallback for generated journals follows the category's kind (income/expense) before cash direction, so customer refunds on unmapped income categories reduce output VAT instead of inflating input VAT; VAT rates are rejected on transfer-like (asset/liability/equity) counter accounts.
- **Validation**: transaction `posted_date` must be a real `YYYY-MM-DD` date; budget months must be real months (`MM` in 01–12); a rejected reconciliation match can no longer be confirmed; re-uncategorising an uncategorised transaction is a no-op instead of audit noise.
- **Merchant normalization** is Unicode-aware ("CAFÉ" ≡ "café") for mappings and recon scoring.

### Removed
- **The legacy cloud stack.** The previous implementation — React frontend on Cloudflare Workers with a Supabase backend, including its orgs/billing/hosted-auth concepts — has been removed from the tree; it remains in git history. Cloud concepts do not return: no hosted service, no telemetry, no central server of any kind.
