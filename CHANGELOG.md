## [0.1.0] — 2026-08-06

**The genuine first release.** No version of this product has ever actually been tagged or published — the two version numbers that previously appeared in this file (`0.1.0` and `0.2.0`, dated 2026-07-19) existed only as local development milestones; no tag ever reached the remote and no GitHub Release was ever published. This entry consolidates everything built since the rewrite — a fully local, self-hosted product: Rust core, Tauri 2 desktop app, embedded SQLite, zero default network calls — through today, as the one real release history starts from. Architecture contract in [docs/ARCHITECTURE.md](docs/ARCHITECTURE.md).

### Added
- **Rust workspace foundation** — `slipscan-core` (domain model, SQLite storage with embedded migrations, service layer: books, accounts, transactions, categories, budgets, documents, double-entry ledger, VAT, reconciliation, reports, append-only audit log) and `slipscan-cli` (`init`, `import`, `extract`, `mail-sync`, `recon`, `report`, `pack`, `vault`, `serve`, `list` — CSV export lives on `report … --csv`, there is no separate `export` subcommand).
- **Global by default — region profiles.** Nothing country-specific is code: chart-of-accounts seeds, tax rate tables, and tax-report labels ship as selectable region profiles (`za` for South Africa — where the tax summary is labeled "VAT201" — and a `generic` profile with a configurable standard rate that works in any country). Bank statement presets are region-namespaced (five SA banks + eight generic international CSV conventions + a custom column mapper), and builtin packs include a global `intl-starter` merchant taxonomy alongside the SA packs.
- **Multi-currency FX via [OpenRate](https://github.com/vul-os/openrate)** — strictly opt-in (no endpoint configured means zero FX network calls): decimal-only rate parsing (floats never touch money), exact 256-bit integer conversion with banker's rounding, a local rate cache with `as_of`/quality-grade/staleness provenance, every conversion recording the exact rate it used; surfaced on CLI (`slipscan fx`), server routes, and desktop Settings.
- **Tauri 2 desktop app** (`apps/desktop`) — Svelte 5 + TypeScript + Vite + Tailwind v4; IPC commands as thin adapters over core services, with hand-maintained TypeScript payload mirrors.
- **Credential vault** — OS-keychain-rooted secret storage (`keyring`-backed `SecretStore`), envelope-encryption design with write-only semantics: secrets can be set, replaced, revoked, and used — never viewed. Design: [docs/THREAT-MODEL.md](docs/THREAT-MODEL.md).
- **Ingestion framework** (`slipscan-ingest`) — `MailboxConnector` trait for user-owned mailboxes (IMAP + IDLE; Gmail history deltas with Pub/Sub pull; Microsoft Graph delta with device-code flow; Proton via local Bridge), `BankAdapter` trait for local, auditable per-bank adapters, and file import/watch (`slipscan watch <dir>` scans a drop folder and keeps importing as files land, content-hash deduped, `--once` for cron/launchd). Guides: [docs/EMAIL.md](docs/EMAIL.md), [docs/BANK-ADAPTERS.md](docs/BANK-ADAPTERS.md).
- **Extraction pipeline** (`slipscan-extract`) — slip-v2 schema (line items, categories, discounts, VAT) with pluggable BYO-key or local LLM/OCR providers; document status machine `pending → extracted → reviewed`.
- **Signed classification packs** (`slipscan-packs`) — category taxonomies + merchant rules as ed25519-signed manifests, TOFU signer pinning, verified on install; corrections stay local. **Pack distribution with no registry** — the same signed bytes over `file:`, `folder:`, `git:` or `https://`, because the signature is what is trusted and not the channel; publishers own a directory named for their key fingerprint so two people sharing one folder never collide; `pack source add|remove|list`, `pack fetch`, `pack pull` and `pack publish` on the CLI; no built-in source and no default URL anywhere in the tree, so a fresh install makes zero pack network calls. Seed packs (`builtin::install_seed_packs`) are reachable as an explicit user action — `slipscan pack seed`, `POST /api/v1/pack_install_seeds`, and a Packs-screen button — opt-in, idempotent, never automatic. `pack_uninstall` and `pack_benchmark` are reachable over HTTP and CLI, the latter comparing a book's own local spend against pack taxonomy (reading only; benchmark **contribution** and its differential privacy remain unimplemented). Guide: [docs/PACKS.md](docs/PACKS.md).
- **Headless self-host server** (`slipscan-server`) — axum wrapper over the same core services, `/api/v1` operation-per-route, binds `127.0.0.1:7151` by default with LAN bind as explicit opt-in. Guides: [docs/SELFHOST.md](docs/SELFHOST.md), [docs/API.md](docs/API.md).
- **Payments — reference watches and signed webhooks.** Watch reference codes on inbound transactions (a flat list — whole-token matching, optional exact amount + currency) and fire HMAC-SHA256-signed webhooks (timestamp + nonce headers, receiver-verifiable, replay-safe) to endpoints you register. Signing secrets are generated locally, held write-only in the credential vault, and shown exactly once; deliveries queue in SQLite with exponential backoff (1m → daily, 20-attempt cap) and carry metadata only — never account numbers or raw bank descriptions. Surfaced as `slipscan pay` on the CLI, `pay_*` server routes (secret-bearing operations refused over HTTP), a serve-mode delivery loop, a `mail-sync` flush, and the desktop Payments panel. Guide with a receiver verification example: [docs/PAYMENTS.md](docs/PAYMENTS.md).
- **Movable data folder + bring-your-own-backup.** One data folder (SQLite + documents) relocatable from desktop Settings and `slipscan data move` via a verified copy (exclusive-lock WAL quiesce, per-file SHA-256, open/migrate + integrity check, fsync-durable atomic pointer swap, old copy removed only after the verified swap), resolved identically by CLI/server/desktop; backup is the user's own cloud sync on that folder (no SlipScan backup service; the keychain KEK never travels with it).
- **UI/UX design system** — oklch elevation hairlines, grain overlay, motion tokens with a staggered route-enter reveal, branded focus-visible rings, display numeric scale, unified chips; per-screen polish across all routes with token-palette charts and semantic budget bars; responsive down to ~740px with a collapsing sidebar rail.
- **Trade reaches the ledger — stock movements post double-entry journals** (migration `0016_ledger_trade`). A goods receipt posts DR Inventory / CR Accounts Payable; confirming a sale posts DR COGS / CR Inventory alongside DR Accounts Receivable / CR Revenue and VAT Output; recording a payment posts DR Bank / CR Accounts Receivable. Cancelling a confirmed order **reverses rather than deletes**, since SQLite itself refuses to amend a posted journal (`journals_no_update`/`journals_no_delete` triggers, standing since `0001_init`). Posting is idempotent, refuses to write into a locked period, and posts nothing (saying so) when a book has no chart of accounts. Revenue is recognised **exactly once per sale, on the path matching how the sale happened** — at confirm for an order-backed sale, at issue for a standalone invoice.
- **Every financial report takes a date range, so a filing period is expressible.** `journals.posted_date` is now routed through every report on every surface, which is what makes a VAT201 for a filing period producible at all. Core's date-aware implementations are a strict superset of the earlier duplicate report code in `slipscan-server::ops`, which was deleted rather than reconciled — one accounting engine.
- **Period close — `close check`, `close run`, `close reopen`.** `close check` is a dry run reporting exactly what `close run` would do; `close run` locks the period; `close reopen` is deliberate, audited, and refuses without a reason. What blocks a close is deliberately narrow: only a broken trial balance or a close dated before an existing one — uncategorised transactions, unreconciled lines, draft orders and unpaid invoices are advisories, not blockers.
- **Purchasing, sales and invoicing, and net worth over time.** Purchase orders with goods receipts against them. Sales orders moving draft → confirmed → paid, with an immutable invoice entity, gapless per-book numbering (a single atomic `INSERT … ON CONFLICT DO UPDATE … RETURNING`, so the number and its reservation cannot come apart under concurrency), recorded payments, derived paid/unpaid status, and an aged receivables view. `networth_snapshots` captures a balance series and backfills one from existing history. Multi-device invoice numbering remains unsolved (see device sync, below).
- **Quotes / estimates** (migration `0014_sales` addendum). `quotes`/`quote_items` share the sales-order line shape but move through their own status machine — `draft → sent → accepted | declined | expired` — and never touch stock or the ledger: a quote is a priced offer that has not happened yet. `quote_accept` turns a `sent` quote into a brand-new draft `sales_orders` row by copying its lines, the same starting point any other freshly created order has. Quotes get their own numbering series (`"quote"`), entirely separate from `sales_orders`' `"sales_order"`. Full CLI (`slipscan quote …`), HTTP (`quote_create`/`_get`/`_list`/`_update`/`_delete`/`_item_add`/`_items_list`/`_item_update`/`_item_remove`/`_send`/`_decline`/`_expire`/`_accept`/`_totals`), and a desktop Quotes screen. Deliberately out of scope: no e-mailing a quote, no PDF.
- **Fixed-asset register with depreciation** (migration `0016_assets`). `assets` holds a person's own capitalisation record (cost, acquisition date, useful life, method) — editable right up until depreciation exists against it. `asset_depreciation_runs` holds one immutable fact per (asset, period) actually posted to the ledger — never edited, never deleted, same shape as `po_receipts` and `networth_snapshots`; a correction is a new fact (a journal reversal), not an edit. Straight-line and reducing-balance methods; each depreciation run posts DR Depreciation Expense / CR Accumulated Depreciation; `asset_dispose` reverses any depreciation posted after the disposal period. Full CLI (`slipscan asset …`), HTTP (`asset_create`/`_get`/`_list`/`_update`/`_dispose`/`_with_depreciation`), and a desktop Assets screen.
- **Recurring schedules — repeating invoices and transactions** (migration `0017_recurring`). A template (`recurring_schedules`/`recurring_schedule_items`) plus a pure recurrence-arithmetic function, `occurrence_date(start_date, frequency, interval_count, occurrence_index)`, that always reapplies the **anchor day from `start_date` itself** — never from the previous occurrence's already-clamped result — so a schedule anchored on the 31st reads 31, 28 (or 29), 31, 30, 31, … through a year instead of ratcheting down to the 28th the first time it crosses February; the identical rule extends `Yearly` to a 29 February anchor. **Nothing fires by itself** — there is no scheduler or daemon anywhere in this product; a schedule becomes due and stays inert until `recurring_run_due` is called from the CLI, an HTTP call, the desktop app, or a cron a user points at `slipscan recurring run-due`, and generates only what is due *as of that call*, once. It reuses the existing invoice (`invoice_issue`) and transaction (`transaction_create`) paths verbatim — every rule those already enforce (numbering, VAT, the revenue/AR journal, the merchant-mapping cascade, dedupe) applies unchanged, because a schedule-generated record *is* one, made by the same code; running the same `as_of` twice does not double-create (a repeat returns the earlier result rather than erroring or duplicating; the server maps the underlying conflict to `409`). Full CLI surface: `create`, `get`, `list`, `due`, `update`, `pause`, `resume`, `delete`, `item-add`, `item-list`, `item-update`, `item-remove`, `preview` (a dry run showing upcoming occurrence dates without generating anything), and `run-due`. Every replicated table involved is wired into `slipscan-sync`'s capture: `recurring_schedules`/`recurring_schedule_items` as LWW state (a person keeps editing the template), `recurring_runs` as an OR-Set of immutable per-occurrence facts. **CLI-only** — no HTTP routes and no desktop screen yet.
- **Desktop screens for Phase 6** — Contacts, Catalogue, Stock, Purchasing, Sales (orders, invoices, aged receivables), Quotes, and Assets, each gated on the book profile so a household book is not shown a purchase order.
- **A signed operation log — phase 2 of the node model, and still nothing syncs.** Every change to a replicated table is recorded as one DMTAP Sync operation (`substrate/SYNC.md` §4), individually signed with the device key phase 1 minted (RFC 9052 `COSE_Sign1`, EdDSA), ordered by a persisted HLC, stored in the same SQLite file as the books. Capture is a **SQLite trigger per replicated table** (migration `0700_oplog`), asserted equal to `slipscan-sync`'s mapping registry in both directions, so a table added without a sync decision fails the suite rather than replicating by accident or silently not replicating. An operation has exactly one identity — the §4.1 content address, as the primary key. Money stays `i64` minor units end to end. The posted ledger's immutability carries through: `journals`/`journal_lines` carry an insert-only capture trigger, so a correction remains a reversal. **There is still no transport and no apply path** — pairing two devices still changes nothing about your data. [docs/NODES.md](docs/NODES.md#what-is-still-missing).
- **Per-device identity and pairing — phase 1 of the node model, and nothing syncs.** An ed25519 keypair per device whose public half *is* the device id, private half in the write-only vault; migration `0600_devices`; peers pinned trust-on-first-use, a key change is a refusal rather than a silent re-pin, a revoked peer becomes a tombstone that cannot re-pair itself; identity rotation must be signed by the key it replaces; 9-word key-names so two people can compare a fingerprint out loud. **No accounts anywhere in it** — no email, password, username, login, or server that decides who you are. `slipscan device` runs the whole ceremony; over HTTP only the public half is served, while anything creating key material or carrying a claim token is local-only and answers 403 with the command to run. No Devices screen in the desktop app. [docs/NODES.md](docs/NODES.md).
- **Bank-alert emails become transactions, with no bank's format in the product.** `slipscan mail-sync --alerts --account <acct>` parses a matched alert into a `StatementLine` and imports it through the same `import_statement_lines` function CSV and scraper imports call, so dedupe, categorisation and Payments detection all apply without a second implementation. Formats arrive as a third pack kind, `mailrules`, inheriting ed25519 signing, TOFU pinning and per-book install; **SlipScan ships no bank patterns at all**. The parsing engine contains no bank, country, currency or date-order literal, and declines with a reason (a letter inside a captured amount, a decimal separator disagreeing with the rule's style, a date outside drift window, a contradicting account hint) rather than guessing. CLI-only, one target account per run, no desktop screen: [docs/EMAIL.md](docs/EMAIL.md#bank-alert-emails--transactions).
- **[PARITY.md](PARITY.md) — measured parity matrices** against the Xero and Vault22/22seven axes: 24 capabilities, each scored Built / Partial / Not built with a link to the file that justifies the score, plus a ranked gap list. `npm run docs:check` fails if any citation stops resolving.
- **`brand/` is the one source for brand assets**, enforced by `brand:check` (`scripts/sync-brand.ts` mirrors masters outward and fails CI on drift).
- **CI gates that are mutation-tested, not assumed**: `parity:check` (API surfaces match documented claims), `reachable:check` (no finished core capability is left unreachable from every surface — see Fixed, below), `mock-guards:check` (the desktop mock's guards agree with core's), `tests:check` (every test asserts something, nothing skipped, no `todo!()` ships), `source:check` (no source file is silently binary). Each was broken deliberately, confirmed red, then reverted, to prove it actually catches its own failure mode.
- **Documentation set** — getting started, configuration, email, bank adapters, packs, benchmarks, self-host, API, threat model, screenshots, FAQ, nodes, payments under `docs/`; root `SECURITY.md` reporting policy.
- **Release packaging** — Tauri bundles for macOS/Windows/Linux and a tag-triggered CI release workflow (version-match guard across every file that carries the product version, draft releases, commented signing hooks); Playwright screenshotter (`npm run screenshot`) keeps README/site/docs screenshots real.

### Fixed
- **A JSON `null` could not clear a nullable field on any HTTP endpoint, silently.** `Option<T>`'s `Deserialize` maps `null` to `None` without descending, so on an `Option<Option<T>>` patch field `{"note": null}` and `{}` arrived identical: an absent key and an explicit null were indistinguishable, and every clear was read as "leave unchanged." Every patch type the HTTP API accepts was affected — ten of them — and the failure was quiet in the worst way: the request succeeded, returned 200, and left the field exactly as it was. Fixed with a `double_option` deserializer, now carried by 23 annotated fields, plus a source-level coverage test so a new nullable field cannot be added without one. The desktop escaped this only because `dto.rs` hand-rolled `clear_*` booleans to work around it; those are deleted, and one convention now covers every surface.
- **Contacts, the catalogue and the stock ledger were complete and reachable from almost nothing.** All three were finished at every layer — schema, repo, service, tests — and wired to no meaningful surface: contacts on 1 of 7 operations, the catalogue 1 of 16, and **the stock ledger 0 of 9**. Meanwhile purchasing and sales wired all of their own operations onto foundations a user could not put a row into, because an order needs a `contact_id` and a stock line needs a `variant_id`. Every layer individually complete, every test green, and nothing detected it. All three are now on the CLI, the HTTP API, desktop IPC and the TypeScript client; `npm run reachable:check` is the ratchet that keeps them there, comparing every public `CoreService` method against the surface sources with test modules stripped, because a method called only from `#[cfg(test)]` looks wired and is not.
- **Pack rules are applied on every surface, not just where a pack was installed.** `slipscan_packs::register_classifier()` documents itself as "call it once at startup, in every binary that imports transactions," and no binary did — registration only happened inside `pack_install`. A process that had not installed a pack *that run* therefore skipped every `contains`, `regex` and `keyword` rule already in the database; only `merchant_exact` rules kept working, because installs seed those into core's own `merchant_mappings`. The CLI's `main()` and the desktop's `run()` now register at startup, covered by a before/after test on each surface.
- **Reversal-aware correction path** (migration `0201`): a generated journal that has been reversed no longer blocks regenerating a corrected journal for the same transaction/document, and reconciliation now treats a journal reinstated by reversing its reversal as matchable again. Uniqueness is enforced as "one *net-live* generated journal per source" in the service layer.
- **VAT classification**: the counter-account fallback for generated journals follows the category's kind (income/expense) before cash direction, so customer refunds on unmapped income categories reduce output VAT instead of inflating input VAT; VAT rates are rejected on transfer-like (asset/liability/equity) counter accounts.
- **Validation**: transaction `posted_date` must be a real `YYYY-MM-DD` date; budget months must be real months (`MM` in 01–12); a rejected reconciliation match can no longer be confirmed; re-uncategorising an uncategorised transaction is a no-op instead of audit noise.
- **Merchant normalization** is Unicode-aware ("CAFÉ" ≡ "café") for mappings and recon scoring.

### Changed
- **The repo's own JavaScript is now TypeScript — all seventeen files.** The root gate scripts in `scripts/`, the desktop app's build and screenshot scripts, and the app's API client, all under Node's native type stripping (no bundler, no build step for them). `svelte-check` coverage went from 238 to **364 files**, because the converted files had been outside `tsconfig.json` and type-checked by nothing at all. The only JavaScript left in the tree is vendored third-party code (`mermaid`, `marked`). **The Rust crates are untouched** and stay Rust. TypeScript moved 5.9 → **6.0.3**, deliberately not to 7: 7 is the compiler rewritten in Go and does not expose the JavaScript compiler API `svelte-check`/`svelte2tsx`/`typescript-eslint` call into, all three capped at 6.
- **The desktop app has a type-aware lint gate, deliberately a small one.** The full `typescript-eslint` recommended-type-checked set was measured against this tree first and produced 496 findings containing exactly one real defect (an `api.health()` chain with no `.catch()`). The shipped `eslint.config.mjs` is an allow-list of rules measured to carry signal here, with each excluded rule's evidence recorded next to it.
- **The desktop app's `lib/` is grouped by what each module is** — `state/` for the rune stores, `util/` for dependency-free helpers — rather than seventeen loose files at one level.
- **README** rewritten for the standalone product: centered wordmark, plain-text badges, hero screenshot, screenshot gallery, quick start, architecture + decentralized-network diagrams, and a full documentation table.

### Removed
- **The legacy cloud stack.** The pre-rewrite implementation — a React frontend on Cloudflare Workers with a Supabase backend, including its orgs/billing/hosted-auth concepts — has been removed from the tree; it remains in git history. Cloud concepts do not return: no hosted service, no telemetry, no central server of any kind.

### Known limitations
- **No device sync yet.** Per-device identity and a signed operation log both exist (above), but there is no transport and no apply path — pairing two devices changes nothing about your data.
- **No live bank adapter ships.** SlipScan ships zero bank-specific parsing; bank-alert and statement formats arrive only through signed packs you install yourself.
- **Recurring schedules are CLI-only** — no scheduler/daemon, no HTTP route, no desktop screen; a schedule must be triggered by a person or a cron they set up.
- **Multi-device invoice numbering is unsolved** — moot for now, since nothing syncs between devices.
- **No differential-privacy benchmark contribution.** Comparing your own spend against an installed benchmark pack is local-only; nothing is ever sent back.
- **No drag-and-drop document capture** anywhere in the desktop app.
- **No report converts multi-currency figures.** FX conversion exists (above) but no routed report applies it yet.
- **No push loop runs on any surface** — IMAP IDLE and Gmail Pub/Sub pull stay library-only; Microsoft Graph push is unsupported by design outside self-host mode.
